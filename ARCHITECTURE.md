# Архитектура приложения

## Общая схема

Приложение состоит из трех основных слоев:

1. **UI Layer** - пользовательский интерфейс (PySide6)
2. **Core Layer** - бизнес-логика и сервисы
3. **Jira Layer** - получение задач Jira по источникам и кэширование
4. **LLM Layer** - профили OpenAI-совместимых API и запросы для директивы `{@llm}`

## Поток выполнения

### Обработка горячей клавиши

1. Пользователь нажимает глобальную горячую клавишу (по умолчанию `Ctrl+=`)
2. `pynput` перехватывает комбинацию и вызывает обработчик в `Application`
3. `Application` захватывает выделенный текст через `ClipboardService`
4. Для глобальной клавиши открывается `CommentDialog`
5. Пользователь выбирает комментарий
6. Если комментарий привязан к Jira-источнику:
   - Получаются задачи из `JiraIssuesService`
   - При единственной задаче выполняется авто-выбор
   - Исключение: если показаны данные из устаревшего кэша без успешного обновления, всегда показывается `IssueDialog`
7. `Application` восстанавливает фокус исходного окна
8. `ClipboardService` обрабатывает текст:
   - Симулирует `Ctrl+C`
   - Читает буфер
   - Применяет шаблон (`render_text`)
   - Записывает в буфер
   - Симулирует `Ctrl+V` (`paste_text`)

### Шаблон с директивой `{@llm}` (долгий путь)

Рендер такого шаблона включает сетевой запрос на секунды, поэтому он не
выполняется в главном потоке и не идет сразу после восстановления фокуса:

1. `Application._process_text` определяет по `TemplateEngine.uses_llm()`, что
   шаблон требует LLM, и уходит в `_start_llm_flow`; исходный буфер обмена
   возвращается пользователю на время ожидания
2. Проверяется, что у комментария выбран существующий профиль (`Comment.llm_profile`)
3. Показывается `LlmProgressDialog` (application-modal, поверх окон, кнопка
   `Отмена`); повторные горячие клавиши игнорируются по флагу `_llm_request_in_progress`
4. `ClipboardService.render_text()` выполняется в `threading.Thread`;
   директива `{@llm}` через `TemplateEngine._llm_resolver` попадает в
   `Application._resolve_llm`, который находит профиль и вызывает `LlmClient`
5. Результат возвращается в главный поток через `AppSignals.invoke_in_main_thread`;
   диалог закрывается, затем (через `QTimer.singleShot(0, ...)`) восстанавливается
   фокус окна назначения и вызывается `ClipboardService.paste_text()`
6. Ошибка (`TemplateRenderError`: нет профиля, таймаут, HTTP-ошибка, пустой
   ответ) — ничего не вставляется, показывается `QMessageBox`; отмена —
   результат потока отбрасывается по `cancel_event` (прервать `urllib` нельзя,
   поток доработает до ответа или таймаута)
7. Если после `SetForegroundWindow` активно не окно назначения, результат не
   вставляется вслепую, а копируется в буфер обмена с уведомлением

## Ключевые компоненты

### MainWindow
- Управление настройками
- CRUD операции с комментариями
- Перетаскивание строк комментариев для изменения порядка (без автосохранения в файл)
- Системный трей
- Команда "Обновить источники" в меню трея

### CommentDialog
- Выбор комментария
- Поиск и фильтрация
- Модальное окно always-on-top

### LlmProgressDialog
- Окно ожидания ответа LLM: статус («Запрос N из M к профилю …»), счетчик секунд, кнопка `Отмена`
- Показывается через `show()` без вложенного event loop; закрытие любым способом до завершения считается отменой (`cancelled`)
- Одноразовое: удаляется после закрытия (`WA_DeleteOnClose`), на каждый запрос создается новое

### IssueDialog
- Выбор задачи Jira из списка
- Поиск и фильтрация
- Кнопка `Обновить` для повторного запроса к источнику
- Обновление списка выполняется асинхронно (в фоне), UI остаётся отзывчивым
- Кнопка `OK` назначена кнопкой по умолчанию (Enter)

### HotkeyManager
- Регистрация глобальных хоткеев
- Использует `pynput`

### ClipboardService
- Симуляция Ctrl+C/V
- Чтение/запись буфера (через pyperclip)
- Применение шаблонов и нормализация отступов — `render_text()` (чистая функция, может выполняться в фоновом потоке)
- Вставка готового текста — `paste_text()` (буфер → Ctrl+V → восстановление буфера)
- `process_captured_text()` = `render_text` + `paste_text`, быстрый путь для шаблонов без `{@llm}`
- Сохранение и восстановление исходного буфера обмена

### TemplateEngine
- Обработка макросов, модификаторов и блочных директив
- Поддерживаемые макросы:
  - `{text}` - выделенный текст
  - `{date}`, `{time}`, `{datetime}` - время
  - `{author}` - автор из настроек приложения
  - `{issue_key}`, `{issue_summary}` - Jira
- Поддерживаемые расширения:
  - `{text|prefix="..."}` - префикс каждой непустой строки `{text}`
  - `{@line_limit ...}{@end}` - ограничение длины строк внутри блока
  - `{@llm}{@end}` - содержимое блока (уже с подставленными макросами) отправляется в LLM, ответ подставляется вместо блока; `raw=true` отключает срезание markdown-ограждений и пробелов по краям
- Движок не знает об HTTP: обработчик `{@llm}` инжектируется через `TemplateEngine(llm_resolver=...)`, профиль приходит в контексте рендера (`context["llm_profile"]`)
- `TemplateRenderError` прерывает рендер целиком (в отличие от прочих ошибок директив, после которых в результат попадает исходный текст блока) — для `{@llm}` такая деградация означала бы вставку промпта в код
- `uses_llm()` / `count_llm_blocks()` — по скомпилированному шаблону, чтобы `Application` выбрал быстрый или долгий путь

### CommentsRepository
- Хранение комментариев в `comments.json`
- CRUD операции
- Поиск по комментариям
- Порядок комментариев хранится в том же порядке, в котором они сохранены в файле

### JiraSourcesRepository
- Хранение Jira-источников в `jira_sources.json`
- CRUD операции через таблицу в окне "Источники" (токены в таблице маскируются); таблица валидируется в `accept()`, при ошибке окно остается открытым с правками
- Для источника доступны `ttl_minutes`, `timeout_seconds`, `auto_refresh`
- Токены на диске шифруются через `SecretStore` (DPAPI), если включена настройка `security.encrypt_tokens` (по умолчанию включена); при загрузке файл приводится к текущей настройке (открытые токены шифруются / зашифрованные раскрываются)

### SecretStore (`core/secret_store.py`)
- Шифрование секретов (токены Jira, ключи LLM) через Windows DPAPI (`CryptProtectData`/`CryptUnprotectData` через `ctypes`, без внешних зависимостей)
- `unprotect_all()` — общая для репозиториев логика: расшифровать список, найти нерасшифровываемые значения, решить, нужно ли пересохранять файл под текущую настройку
- Формат на диске: `dpapi:<base64>`; значение без префикса считается открытым текстом
- Привязка к учетной записи Windows + дополнительная энтропия приложения
- Вне Windows / при ошибке DPAPI значение сохраняется открытым текстом с предупреждением в логе

### LlmProfilesRepository
- Хранение профилей LLM в `llm_profiles.json`: `name`, `base_url`, `model`, `api_key`, `timeout_seconds`, `temperature`
- CRUD через таблицу в окне «Профили LLM» (ключи маскируются); валидация в `accept()`, как у источников Jira
- Ключи API защищаются так же, как токены Jira (`SecretStore`, настройка `security.encrypt_tokens`); общая логика приведения файла к настройке — `secret_store.unprotect_all()`
- Комментарий ссылается на профиль по имени (`Comment.llm_profile`), как на источник Jira; при удалении профиля ссылки в комментариях сбрасываются

### LlmClient
- `POST <base_url>/chat/completions` через `urllib` (без сторонних зависимостей и без стриминга)
- Одно `user`-сообщение, `temperature` передается только если задана в профиле
- Ошибки: `TimeoutError` и `LlmError` (HTTP-статус с сообщением из `error.message`, сетевая ошибка, некорректный JSON, пустой ответ, ошибка с кодом 200)
- В лог пишутся адрес, модель, длины промпта и ответа, время; ключ и тексты — нет

### JiraIssuesCache
- Кэширование задач Jira по источникам
- TTL задается в источнике (минуты)
- `0` отключает кэш, `-1` хранит кэш без срока
- Хранение в `jira_issues_cache.json`

### JiraLastIssueRepository
- Хранение последней выбранной Jira-задачи по источнику в `jira_last_issue.json`
- Используется для поднятия последней выбранной задачи наверх списка в `IssueDialog`

### JiraIssuesService
- Получение задач из Jira REST API (`/rest/api/2/search`)
- Ограничение: максимум 20 задач
- Таймауты берутся из источника (секунды)
- Стратегия `stale-while-revalidate`: при просроченном кэше данные отдаются сразу, а обновление выполняется в фоне
- При отсутствии кэша выполняется live-запрос; при таймауте ошибка возвращается без повторного блокирующего запроса

### Application (автообновление Jira)
- Фоновый планировщик проверяет автообновляемые источники
- Источник обновляется только если `auto_refresh=true` и `ttl_minutes > 0`
- При неактивности пользователя более 60 минут автообновление временно приостанавливается

### Безопасная запись конфигурации
- JSON-файлы конфигурации и кэша записываются через `atomic_write_json(...)`
- Схема записи: временный файл в той же директории -> `flush`/`fsync` -> `os.replace`
- Цель: минимизировать риск повреждения файла при аварийном завершении/отключении питания
- Если `comments.json`/`jira_sources.json` не удалось прочитать, файл переименовывается в `<имя>.broken-<метка>` (`backup_corrupted_file`), а пользователю показывается предупреждение — последующий `save()` не затирает исходные данные

### Взаимодействие фоновых потоков с UI
- Фоновые воркеры (`threading.Thread`) не имеют Qt event loop, поэтому `QTimer.singleShot` из них не срабатывает
- Результат в главный поток возвращается только через сигналы: `AppSignals.invoke_in_main_thread(callable)` в `Application` и `IssueDialog.refresh_completed`
- Рендер шаблона с `{@llm}` тоже идет в фоновом потоке; состояние сценария (`_LlmFlowState`: флаг отмены, диалог, счетчик запросов) передается через контекст рендера, чтобы поток отмененного сценария не влиял на следующий

## Точки расширения

### Добавление новых макросов

Зарегистрируйте обработчик в `TemplateEngine._macro_handlers`

### Добавление блочных директив

Зарегистрируйте обработчик `(value, args, context) -> str` в
`TemplateEngine._block_handlers`. Если частичный результат использовать
нельзя, бросайте `TemplateRenderError`.

### Несколько хоткеев

Регистрируйте несколько комбинаций в `_setup_hotkeys()`
